## 一、概念

### `async def` 函数：调用 ≠ 执行

`async def` 定义的是**协程函数**。调用它**只制造一个协程对象**，函数体一行都不执行。

```python
result = hello("q")     # 得到 <coroutine object hello at 0x...>，什么都不打印
```

和**生成器同源**：

| | 调用时 | 靠什么推进 |
|---|---|---|
| 生成器函数（`def` + `yield`） | 不执行，返回生成器对象 | `next()` / `for` |
| 协程函数（`async def`） | 不执行，返回协程对象 | `await` / `asyncio.run()` |

**为什么这么设计**：协程对象必须能被**挂起、能被恢复**，事件循环才有东西可调度。
如果调用就一路执行到底，就没有暂停点，并发无从谈起。

### 驱动协程的两种方式

| 写法 | 谁建事件循环 | 返回值 | 用在哪 |
|---|---|---|---|
| `asyncio.run(coro)` | 自己建一个，用完就关 | 协程的 `return` 值 | **最外层**，整个程序只调一次 |
| `await coro` | 循环**已经**在跑 | 协程的 `return` 值 | 只能在 `async def` 里面 |

⚠️ 不能在 `async def` 里面再调用 `asyncio.run()`。

### `await`：挂起自己 + 让出跑道

```python
await asyncio.sleep(1)
#     └── 造一个协程对象   └── 交给事件循环：这 1 秒我不占着跑道
```

**两个要点**：

1. `await X` 的**求值结果 = `X` 里面 `return` 出来的东西**（这才有了「接回返回值」这回事）
2. 让位是并发的**唯一来源**。不让位的代码，asyncio 拿它一点办法都没有

**和 `Thread.join()` 的区别（重要）**：

| | `t.join()` | `await coro` |
|---|---|---|
| 挡住谁 | **整个线程**真的睡死，一行 Python 都不执行 | 只挂起**当前这个协程**，事件循环照常运行 |
| 等什么 | 一个操作系统线程结束 | 一个协程跑完 |
| 返回值 | **永远是 `None`** | 协程的 `return` 值 |
| 恢复靠谁 | 操作系统调度 | 事件循环把协程捡回来接着跑 |

> **一句话：`join()` 是「站着干等」，`await` 是「站到一边去，把跑道让出来」。**

### ⭐ 并发必须同时满足两个条件

1. 任务会**让位**（`await` 真正的 I/O）
2. 同一时刻**有多个任务在等**

**缺任何一个，都没有并发。** 这是今天所有实验的总纲：

| 实验 | 会让位 | 多个任务在等 | 实测 |
|---|---|---|---|
| ex2 串行 `await` | ✅ | ❌ 一次只交一个任务 | **4.50s**（3 × 1.5s）⚠️见踩坑 1 |
| ex3 `asyncio.gather` | ✅ | ✅ | **1.00s** |
| ex4 `gather` + `time.sleep` | ❌ | ✅ | **3.00s** |

### `asyncio.gather`：主业是**并发**，不是「存返回值」

| # | 干什么 | 地位 |
|---|---|---|
| 1 | 把多个协程**一次性**交给事件循环，让它们同时跑 | 🥇 **主业** |
| 2 | 等它们**全部**完成 | 🥈 |
| 3 | 把各自的 `return` 值按**传入顺序**收成一个 **list** 返回 | 🥉 附带 |

- 收到的是**一串协程对象**（位置参数），**不是 list**；`*(...)` 是解包
- 内部把每个协程包装成 **`Task`**，一次性交给事件循环 → 这就制造出了「多个任务在等」
- 返回的 list **顺序 = 传入顺序**，**不是**完成顺序
- 它自己也是 awaitable，**必须 `await`**；漏了 → 零报错但一行不执行

**保存在哪里？** 是你自己的变量保存的：

```python
results = await asyncio.gather(...)
#  ↑            └── gather 只负责「并发 + 收集成 list 交给你」
#  你保存
```

### 和 Day 22 的 `Future` 对上号

| | 线程池（Day 22） | asyncio（Day 23） |
|---|---|---|
| 提交一个任务 | `executor.submit(fn)` → **`Future`** | `asyncio.create_task(coro)` → **`Task`** |
| 等一个并拿结果 | `future.result()` | `await task` |
| 等一批 | `as_completed(...)` | `await asyncio.gather(...)` |
| 靠什么并发 | **多线程** + 操作系统调度 | **单线程** + 协程主动让位 |

（`Task` 就是一种 `Future`。）

### 三种并发怎么选

| | 开销 | 能撑多少并发 | CPU 计算 |
|---|---|---|---|
| 线程池 | 中（每线程 MB 级栈） | 几百 | ❌ 受 GIL 限制 |
| 进程池 | 高（独立解释器） | 跟核数有关 | ✅ 唯一能真加速 |
| **asyncio** | **极低（Task 只是对象）** | **几千** | ❌ 反而不如串行 |

**AI 应用开发选 asyncio 的原因**：LLM 调用、向量库查询、HTTP 请求**全是「等」**，
而一个 RAG 服务要同时处理成百上千个请求。计算不靠它，等待才是它的主场。

## 二、代码

| 文件 | 教什么 | 关键点 |
|---|---|---|
| `ex1.py` | 协程对象 vs 普通函数 | `hello("q")` 只造对象；`asyncio.run(...)` 才执行 |
| `ex2.py` | `await` 是**串行** | 三个 `await` 排队 = 耗时相加 |
| `ex3.py` | `gather` 并发 | 三个任务同时等，耗时 = 单个任务的耗时 |
| `ex4.py` | `asyncio.sleep` vs `time.sleep` | 同一个 `gather`，1.00s vs 3.00s |
| `benchmark.py` | 三组**控制变量**对照 | 串行 / gather / gather+`time.sleep` |

### ex1 的关键观察

```python
result = hello("q")              # 协程对象，不执行
asyncio.run(result)              # 真正执行；返回值 = hello 的 return（没写 return → None）
```

**`asyncio.run()` 是有返回值的** —— 返回协程 `return` 的东西。ex1 里 `hello` 没写 `return`，所以是 `None`。

### ex2 的关键观察

```python
await job("q", 1)   # 把 q 交出去，等它彻底跑完
await job("b", 1)   # 上一行结束，b 才被创建
```

**`await` 让位之后，跑道上只有这一个任务**，事件循环只能干等它 —— 这就是「条件 ②」不满足的样子。

### ex4 的关键观察

```python
async def bad(name, delay):
    time.sleep(delay)      # ❌ 不让位：按住唯一的那条线程
```

同一个 `gather`，`good` 走 1.00s，`bad` 走 3.00s。**外壳是并发的，内核不让位，等于没并发。**

## 三、踩坑

### 1. 参数被写死，形同虚设 ⚠️（ex2）

```python
async def job(name, delay):
    await asyncio.sleep(1.5)     # ❌ 写死了 1.5，delay 参数从未被使用

await job("q", 1)                # 传 1 进去，完全被忽略
```

**零报错、程序正常跑完，但实际耗时是 3 × 1.5 = 4.50s 而不是 3.00s。**

**教训：定义参数 ≠ 使用参数。** 改法是 `await asyncio.sleep(delay)`。

**这类「静默错误」今天又出现一次** —— 和 Day 22 的「语法合法、零报错、代码没执行」是同一族。

### 2. `dquote>`：双引号没闭合

```
git commit -m "docs(day22): 补记两条疑问
dquote>                                    ← 卡在这
```

**原因**：开了双引号没闭合，shell 在等你把话说完。这时按回车只会继续显示 `dquote>`，永远执行不了。

**解法**：`Ctrl+C` 整条丢弃（什么都没执行，安全）。

**记忆**：**只要提示符最后一个符号不是 `%`，就说明你还在上一条命令里面。**

同类：`quote>`（单引号）、`heredoc>`、`pipe>`、`cmdsubst>` —— 一律 `Ctrl+C`。

### 3. 中文输入法的全角引号

| | 长相 | 字符 | shell 认吗 |
|---|---|---|---|
| 半角（英文） | `"` | ASCII 34 | ✅ |
| 全角（中文） | `"` | Unicode U+201C | ❌ 只是普通字符 |

**中文输入法开着时敲引号键，出来的是全角引号** —— 于是「明明打了一对引号」还是 `dquote>`。

**解法：敲命令时切英文输入法。**

### 4. 漏写 `await` → 零报错但代码没执行 ⚠️

```
RuntimeWarning: coroutine 'run_serial' was never awaited
```

`serial = run_serial(N)` 拿到的是协程对象而不是数字，后面 `f"{serial:.2f}"` 会直接 `TypeError`。

**这个警告就是报警器：看到 `was never awaited`，回去补 `await`。**

### 5. `time.sleep` 混进协程 → 阻塞整个事件循环

不只是变慢，是**完全失效**（加速比 0.99x —— 比串行还慢 0.03s）。

**原因**：`gather` 创建 `Task`、调度、收集结果的开销**全付了**，但一个让位点都没有，收益为零。

**教训：在协程里只能用 `await asyncio.sleep()`。**

### 6. 从错误的目录运行脚本

提示符是 `~ %` 而不是 `day23_asyncio %`。

这次没事，是因为用了**绝对路径**（VS Code 的 ▶ 按钮生成的）：

```
/Users/hzj/dev/ai-learning/.venv/bin/python /Users/hzj/dev/ai-learning/day23_asyncio/benchmark.py
```

**但涉及相对路径（读 `data/xxx.csv`、写 `output/`）时会直接找不到文件。**

**解法：跑之前 `cd` 到脚本所在目录，并 `pwd` 确认。**

### 7. 字符串里的 typo 不会报错

`print("直接调用hell0（）")` —— `hell0` 是数字 0 不是字母 o。

**在字符串里，typo 完全合法、不报错，只是输出难看。** 但同一个手误写在**变量名或函数名**上就是 `NameError`。

## 四、实测数据

### 实验 A · ex2 / ex3 / ex4（定性对照）

| 实验 | 每任务 | 任务数 | 实测 | 说明 |
|---|---|---|---|---|
| ex2 串行 `await` | 1.5s ⚠️ | 3 | **4.50s** | 条件 ② 不满足 |
| ex3 `gather` | 1.0s | 3 | **1.00s** | 两个条件都满足 |
| ex4 `gather` + `asyncio.sleep` | 1.0s | 3 | **1.00s** | 正确 |
| ex4 `gather` + `time.sleep` | 1.0s | 3 | **3.00s** | 条件 ① 不满足 |

⚠️ **ex2 和 ex4 的每任务耗时不同（1.5s vs 1.0s），所以这两组不能直接比时间大小。**
真正控制变量的对照在实验 B。

### 实验 B · `benchmark.py`（控制变量：N 和 DELAY 完全相同）

**N = 10，每个任务 0.2s，理论最优 0.2s**

| 实验 | 耗时 | 加速比 |
|---|---|---|
| 串行 `await` | **2.01s** | 1.00x（基准） |
| `asyncio.gather` | **0.20s** | **10.01x** ✅ |
| `gather` + `time.sleep` | **2.04s** | **0.99x** ❌ |

**读出来的三件事**：

1. **`0.99x` 比 `1.00x` 更有信息量** —— 它比串行还**慢 0.03s**。
   并发外壳 + 阻塞内核 = **开销全付、收益为零，是倒亏**。
2. **`2.04s ≈ 2.01s ≈ 10 × 0.2s`** —— 这是「阻塞事件循环」的**实测定义**：
   `gather` 完全失效，退化成一个接一个睡。
3. **加速比不可能超过任务数 N**：

   ```
   串行耗时 = N × DELAY = 10 × 0.2 = 2.0s
   并发耗时 ≈ DELAY = 0.2s
   加速比上限 = N = 10
   ```

### 三条定律

> **① 纯等待任务的 asyncio 加速比上限 = 任务数 N。**
> N=10 → 10.01x（已顶格）。想更高只能加任务数，不能靠「优化」。
>
> **② 加速比只取决于两件事：任务数 + 是否让位**，与用哪种并发机制无关。
> 所以 `gather` + `time.sleep` 的 0.99x 完全自洽。
>
> **③ 三种并发的真正区别不在「峰值加速比」，而在开销、可扩展上限、能否加速 CPU 计算。**

### ⚠️ 和 Day 22 对比时的注意事项

| 实验 | 任务数 | 串行 | 并发方式 | 加速比 |
|---|---|---|---|---|
| Day 22 I/O | 4 | 4.02s | 线程池(4) | **3.99x** |
| Day 22 I/O | 4 | 4.02s | 进程池(4) | 3.67x |
| Day 23 纯等待 | 10 | 2.01s | `asyncio.gather` | **10.01x** |

**不要拿 10.01x 和 3.99x 比大小！** 任务数不同（10 vs 4）：

- Day 22：上限 4，实测 3.99x → **顶格**
- Day 23：上限 10，实测 10.01x → **顶格**

**两个都跑满了各自的上限，机制上没有优劣之分。**
**变量不同的实验不能直接比较大小** —— 这是做技术选型对比时必须养成的习惯。

## 五、疑问

> 这一节按「当时真实问出来的问题」记 —— 问题都在会话里提过，这里是回头补的整理，不用特意去凑。

**① `await` 是不是就等于线程里的 `join()`？**

一半对。两个都会「等」，但等的时候谁在干活完全不同：

| | `t.join()` | `await coro` |
|---|---|---|
| 挡住谁 | 整个线程睡死，一行 Python 都不执行 | 只挂起当前协程，**事件循环继续跑别的** |
| 返回值 | 永远 `None` | 协程的 `return` 值 |

`join()` 是「站着干等」，`await` 是「站到一边去，把跑道让出来」。 → 已懂

**② `asyncio.gather` 是不是用来保存返回值的？**

不是。它的主业是**并发**，收集返回值只是附带（按传入顺序打包成一个 list）。
真正「保存」结果的是我自己的变量：

```python
results = await asyncio.gather(...)    # gather 收集好交给我，我负责存
```

→ 已懂

**③ `await` 后面接一个协程，为什么拿到的是它 `return` 的值？**

这个是 Day 24 才彻底解决的：`return` 的值是**装在 `StopIteration` 里被送出来的**，
`await X` 本质上 ≈ `yield from X.__await__()`，所以接得到货。
详见 `day24_event_loop/notes.md` 第六节。 → 已懂
