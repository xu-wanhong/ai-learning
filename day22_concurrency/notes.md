## 一、概念

### GIL（全局解释器锁）

**任何时刻，一个 Python 进程里只有一个线程能执行 Python 字节码。**

所以多线程做**计算**任务不会变快 —— 线程们只是轮流用 CPU，还要额外付出切换开销。

### 为什么线程做 I/O 就有效

因为**等待时会释放 GIL**：

```
线程1: [用CPU] [等网络.......] [用CPU]
线程2:         [用CPU]           ← 趁线程1等待，抢到 GIL 干活
```

`time.sleep()`、网络请求、文件读写都属于这种情况。

### 为什么进程能突破 GIL

每个进程有**独立的 Python 解释器**和**独立的 GIL**，操作系统把它们分配到不同 CPU 核心上，真正并行。

代价：进程间不共享内存（通信要序列化）；启动要重新导入模块，开销大。

### 选型依据

```
在「算」（CPU 密集）  →  进程池
在「等」（I/O 密集）  →  线程池（少量并发）/ asyncio（大量并发）
```

**判断方法：问自己「这个任务是在算，还是在等？」**

## 二、代码

### 线程池 vs 进程池：只差一个类名

```python
from concurrent.futures import ThreadPoolExecutor     # I/O 用
from concurrent.futures import ProcessPoolExecutor    # CPU 用

with XxxPoolExecutor(max_workers=4) as ex:
    results = list(ex.map(func, data))
```

其他代码一个字都不用改。

### 测耗时用 `time.perf_counter()`

不用 `time.time()` —— 后者是墙上时钟，系统对时会导致跳变（甚至算出负数）。
`perf_counter` 是单调递增的高精度计时器。

### `map` vs `submit`

| | `map` | `submit` |
|---|---|---|
| 提交粒度 | 一批 | 一个 |
| 返回 | 结果迭代器 | `Future` |
| 结果顺序 | 输入顺序 | 由 `as_completed` 决定 |
| 单任务失败 | 中断迭代，后续结果丢失 | 隔离，其他不受影响 |
| 适合 | 纯计算、不失败、要顺序 | 有 I/O、可能失败 |

**AI 应用开发几乎都用 `submit` + `as_completed`** —— API 调用必然有超时和失败。

### `max_workers` 是「并发度」

设成 1 就等于没有并发。它影响**速度**，不影响**结果**。

## 三、踩坑

### 1. `args=程序` → NameError

```python
t1 = threading.Thread(target=download, args=程序)
# NameError: name '程序' is not defined
```

**原因**：裸写的中文是**变量名**，不是字符串。Python 去找同名变量，找不到就报错。

### 2. `args=("图片")` 少逗号 → TypeError

```python
args=("图片")     # ❌ 括号不等于元组，这就是个字符串
args=("图片",)    # ✅ 这个逗号才是元组的关键
```

**报错**：`TypeError: download() takes 1 positional argument but 2 were given`

**原因**：字符串被拆成单个字传了进去。

### 3. `t1.start` 少括号 → 静默不执行 ⚠️

```python
t1.start      # ❌ 只是「提到」这个方法，没有调用
t1.start()    # ✅ 加括号才调用
```

**最危险的一类 bug**：语法合法、程序「正常」跑完、没有任何报错，但代码根本没执行。

### 4. `max_workers=1` 结果不变

结果不变是**正确**的 —— 工人数影响**速度**，不影响**结果**（`map` 承诺「结果顺序 = 输入顺序」）。

要看速度差异，任务必须**有耗时**。例 1 的 `n*2` 瞬间完成，所以看不出差别。

### 5. 删 `if __name__` 但保留缩进 → 静默无输出 ⚠️

```python
def work(n):
    return n * n

    with ProcessPoolExecutor(...):    # ← 缩进 4 格，变成 work 的一部分
        print(...)                    #    且在 return 之后 = 死代码
```

**两层问题叠加**：缩进让它归入函数；位置在 `return` 后让它永远执行不到。
最终 `work` 从没被调用 → **零输出，退出码 0**。

**教训：Python 里缩进是语法，不是排版。** 而且「代码没被执行到」不会报错。

### 6. 删掉 `if __name__ == "__main__":` → RuntimeError

```
RuntimeError:
    An attempt has been made to start a new process before the
    current process has finished its bootstrapping phase.
    ...
        if __name__ == '__main__':
```

**原因**：macOS 用 `spawn` 启动子进程，子进程会**重新导入模块**。没有保护 → 无限递归创建进程。

**注意：Python 在报错信息里直接把答案写出来了。** 报错要**先读最后一段**。

### 7. `N` 写成 200000 → 进程池反而更慢（0.31x）

**原因**：进程启动开销（约 0.06 秒）是**固定**的。任务只有 0.005 秒时，开销是它的 12 倍。

**教训：进程池不适合轻任务。** 任务越小，启动开销占比越大，最终可能亏本。

### 8. 数字位数数错（连续两次）

`2000000`（200 万）vs `20_000_000`（2000 万）—— 差一个零，差 10 倍。

**解法：用下划线分隔**，从右往左每三位加一个：

```python
N = 20_000_000    # 20 | 000 | 000，一眼可读
```

## 四、实测数据

### 实验 A · CPU 密集（4 个计算任务）

| N | 串行 | 线程池 | 进程池 |
|---|---|---|---|
| 20 万 | 0.02s | 1.07x | **0.31x** |
| 200 万 | 0.21s | 1.25x | 1.92x |
| 500 万 | 0.43s | 1.06x | 2.32x |
| 2000 万 | 1.86s | 1.11x | 3.49x |
| 6000 万 | 5.62s | 1.09x | 3.46x |

### 实验 B · I/O 密集（4 个各等 1 秒）

| 串行 | 线程池 | 进程池 |
|---|---|---|
| 4.02s | **3.99x** | 3.67x |

### 两条定律

**① 线程池做计算永远 ≈1.1x**
从 20 万到 6000 万，一条平线。**GIL 的影响与任务大小完全无关。**

**② 进程池收益随任务变大而上升**
0.31x → 3.49x。启动开销固定，任务越大占比越小，加速比越接近理论值 4x。
