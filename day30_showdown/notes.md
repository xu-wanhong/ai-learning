## 一、终局总表（`benchmark.py`）

```
机器 10 核 · 任务数 8 · 工人数 8

【等待型】每个 time.sleep(0.3)    串行基准 ≈ 2.4s
  ① 串行          2.44s   ──── 基准 ────
  ② 线程池(8)     0.31s   加速   8.0x
  ③ 进程池(8)     0.39s   加速   6.2x
  ④ asyncio       0.30s   加速   8.1x

【计算型】每个循环 10,000,000 次
  ① 串行          1.78s   ──── 基准 ────
  ② 线程池(8)     1.63s   加速   1.1x     ← GIL 卡死
  ③ 进程池(8)     0.48s   加速   3.7x     ← 真并行
  ④ asyncio       1.65s   加速   1.1x     ← 协程不能算
```

### 怎么读这张表

| 任务类型 | 线程池 | 进程池 | asyncio |
|---|---|---|---|
| **等待型（等 I/O）** | **8.0x** ✅ | 6.2x（浪费） | **8.1x** ✅ |
| **计算型（烧 CPU）** | **1.1x** ❌ | **3.7x** ✅ | **1.1x** ❌ |

> **两个 `1.1x` = GIL 和「协程不能算」的铁证**
> **两个 `8x` = 「等待时可以并发」的铁证**

### `ex2.py` 把这件事做得更干净

**让两种任务都「忙 0.3 秒」**，串行基准都是 ≈2.4s：

```
              任务类型 |       串行 |         线程池(8) |         进程池(8)
--------------------------------------------------------------------
    等待型 time.sleep |    2.44s |     0.31s   8.0x |     0.37s   6.6x
     计算型 纯算术     |    2.53s |     2.35s   1.1x |     0.60s   4.2x
```

**同样"忙"了 0.3 秒，线程池的结果差 8 倍** —— 一个 8.0x，一个 1.1x。

### `ex2.py` 实验②：GIL 最直白的证明

```
  串行             : 1.06s
  2 个线程同时跑   : 0.98s   ← 【没有变快！GIL 在排队】
  2 个进程同时跑   : 0.56s   ← 真并行
```

**两个纯 CPU 循环，各 0.5 秒：**

- 串行 1.0s（当然）
- **两个线程"同时"跑 —— 还是 1.0s**（GIL 让它们排队用同一个核）
- 两个进程跑 —— 0.5s（各有各的 GIL，真并行）

> **这就是 GIL 的定义，用数字写出来了。**

## 二、进程池的启动开销（`ex3.py`）

```
      单个任务规模 |       串行 |     线程池(8) |     进程池(8) |   进程加速比
       200,000 |   0.035s |     0.033s |     0.062s |    0.55x   ← 比串行还慢！
     2,000,000 |   0.359s |     0.329s |     0.138s |    2.60x
    10,000,000 |   1.886s |     1.632s |     0.432s |    4.36x
```

**三个观察**：

| # | 观察 |
|---|---|
| **1** | **20 万次时进程池 0.55x —— 比串行还慢**（启动开销 > 收益） |
| **2** | **任务越大加速比越好**（2.6x → 4.4x）—— 固定开销被摊薄了 |
| **3** | **线程池全程 ≈ 1.0x**（GIL），**和任务大小完全无关** |

> **结论：进程池有「起步价」。单个任务 < 0.1s 就别开进程 —— 用线程或协程。**

### 顺带学到一个技巧：`itertools.repeat`

`cpu_loop(i, loops)` 要**两个参数**，但 `ex.map` 默认只传一个。两种做法：

```python
# ❌ 闭包 —— 会变成嵌套函数，送不进进程池
def make_task(loops):
    def task(i): ...
    return task
# AttributeError: Can't get local object 'make_task.<locals>.task'

# ✅ 多列参数 —— map 会把两列「拉链式配对」
ex.map(cpu_loop, range(N), itertools.repeat(loops))
#      ↑ 函数    ↑ 第一列     ↑ 第二列：loops, loops, loops, ...
```

**`map` 的每一列是一个「参数位」**（和 `zip` 一模一样）：

```
   第一列 range(4)          → [0, 1, 2, 3]
   第二列 repeat(100)       → [100, 100, 100, 100] ...
   配对起来（= zip）        → [(0,100), (1,100), (2,100), (3,100)]
   → 实际调用：cpu_loop(0,100) / cpu_loop(1,100) / ...
```

**三种等价写法**（都能给 map 传两列）：

| 写法 | 线程池 | 进程池 |
|---|---|---|
| **`itertools.repeat(loops)`** | ✅ | ✅ |
| `[loops] * N` | ✅ | ✅ |
| `map(lambda a: f(*a), zip(...))` | ✅ | ❌ **lambda 不能 pickle** |

**选 `repeat` 的理由**：它是**无限重复**，所以**永远和 `range(N)` 对得齐** ——
改 `N` 的时候不会因为它而静默少算。

## 三、混合场景（`ex4.py`）—— 今天的压轴

**16 个任务，每个「先下载 0.3s（I/O），再计算 0.2s（CPU）」**：

```
  A. 全用线程池(4)     :  4.27s
  B. 全用进程池(4)     :  2.31s
  C. asyncio + 进程池  :  1.39s   ← 最快
```

### 为什么 C 最快

| 方案 | 慢在哪 |
|---|---|
| **A 全线程池** | **CPU 部分 16 × 0.2s = 3.2s 全部串行**（GIL 不让路） |
| **B 全进程池** | 每个工人「等 0.3 + 算 0.2」**串着做**，16÷4 = 4 轮 = 2.0s |
| **C asyncio + 进程池** | 等 → **全部并发只要 0.3s**；算 → 丢进程池 16×0.2÷4 = 0.8s |

> **C 的关键是：「等」和「算」被【拆开分别并行】了。**
>
> - `await asyncio.sleep(...)` —— **等**的部分用协程，16 个全叠在一起
> - `await loop.run_in_executor(pool, cpu_fn, i)` —— **算**的部分丢给进程池
>
> **而 A 和 B 都是把「等」和「算」绑死在同一个工人身上** —— 无论哪种工人都要吃亏一头。

### 核心代码只有两行

```python
async def async_mixed(i, pool):
    await asyncio.sleep(IO_TIME)                            # ① 用协程等
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(pool, cpu_only, i)    # ② 丢给进程池算
```

> **这 4 行是 Day 22–30 的全部浓缩**：
> **用协程吃掉 I/O，用进程吃掉 CPU，用 `run_in_executor` 把两者接起来。**

## 四、四种跑法的选择表

| 跑法 | 适合 | 不适合 |
|---|---|---|
| **串行** | 任务很少（< 3 个） | —— |
| **线程池** | **I/O 密集 + 任务量中等**（几十个） | CPU 密集（GIL） |
| **进程池** | **CPU 密集**；任务单个 > 0.1s | I/O 密集（浪费进程）；任务太碎（启动开销） |
| **asyncio** | **I/O 密集 + 任务量很大**（几百上千） | CPU 密集；调同步阻塞老库（要配 `to_thread`） |
| **asyncio + 进程池** | **既有 I/O 又有 CPU 的混合流程** ⭐ | —— |

**一条判据决定一切**：**任务在「等」还是在「算」？**

- **等** → GIL 会释放 → 线程/协程能真并发
- **算** → GIL 不让路 → 线程只能排队 → **上进程**

## 五、踩坑

### ⚠️ 1. `if __name__ == "__main__":` 漏了 → **报错 8 次**

漏了会看到（**而且因为 8 个工人各自重新 import 主模块，会看到 8 遍**）：

```
RuntimeError:
    An attempt has been made to start a new process before the
    current process has finished its bootstrapping phase.
    ...
        if __name__ == '__main__':
        ...
```

> **Python 把修法直接写在报错里了。报错先读最后一段。**

**修法**：**全部逻辑塞进 `main()`，`if __name__ == "__main__": main()`。**

### ⚠️ 2. 嵌套函数 / lambda 送不进进程池

```
AttributeError: Can't get local object 'make_cpu.<locals>.task'
```

**原因**：子进程要靠 `pickle` 把函数序列化过去 —— **"函数内部定义的函数"和 `lambda` 没有模块级的名字，pickle 不了。**

**修法**：**把参数也传过去，函数留在模块级**：

```python
def cpu_loop(i, loops):     # ✅ 模块级
    ...

ex.map(cpu_loop, range(N), itertools.repeat(loops))   # ✅ 用第二列传参数
```

> **⚠️ 注意 `ThreadPoolExecutor` 没有这个限制**（线程在同一进程里，不用序列化）。
> **所以"用 lambda 在线程池里能跑"的代码，换成进程池就炸** —— 这是非常常见的坑。

### ⚠️ 3. 忙等里调了 `time.perf_counter()` → **GIL 实验失效**

**我第一版 `ex2.py` 写错了**：

```python
def spin(seconds):
    t0 = time.perf_counter()
    while time.perf_counter() - t0 < seconds:      # ← ❌ 这里会释放 GIL！
        pass
```

**结果两个线程跑出 0.51s（应该 1.0s）—— 因为 `perf_counter()` 是系统调用，会释放 GIL，两个线程就交替跑了。**

**修法**：**用纯算术循环**（不调任何函数）：

```python
def burn(n):
    x = 0
    for k in range(n):
        x += k * k        # ✅ 纯算术，死抓着 GIL
    return x
```

> **教训**：**"纯 CPU 忙等"里不能出现任何函数调用** ——
> 任何 I/O 或系统调用都会释放 GIL，实验就废了。

### ⚠️ 4. 老坑复现：`ex.map` 的返回值不消费 → 异常被吞

```python
ex.map(fn, range(N))            # ❌ 惰性迭代器，不消费
list(ex.map(fn, range(N)))      # ✅
```

**Day 22 就踩过，今天所有脚本里都用 `list(...)` 包住。**

### 这 9 天真正学到的东西

**① 一条主线**：**并发 = 让「等待」的时间被别人用起来。**

**② 一个判据**：**任务在「等」还是在「算」** —— 决定用线程/协程还是进程。

**③ 一套工具**：线程池 / 进程池 / asyncio / `Semaphore` / `Queue` / `timeout` / `retry` / `run_in_executor`。

**④ 一堆「能跑但错」的坑**：

| 类型 | 例子 |
|---|---|
| **静默错** | f-string 少了 `f`、`=+` 写成 `+=`、`ValueError` 少了 `raise`、`await` 忘了写 |
| **边界错** | 超时阈值卡在正常任务的耗时上 → 误杀 |
| **API 错** | `gather` 少 `*`、`create_task` 收生成器、`as_completed` 用普通 `for` |
| **打字错** | `rusult` / `squaer` / `succes` / `arm` / `o` / `__namee__` / `get[...]` |
| **进程池专属** | 漏 `__main__` 保护、用嵌套函数/lambda |

> **第 ④ 条对面试最值钱** —— **"我知道哪些地方会出错"比"我会背 API"有说服力得多。**
